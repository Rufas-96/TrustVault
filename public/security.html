How TrustVault protects documents

Security model

How TrustVault decides who can reach a document, how it proves who did, and what taking access away means.

Roles

A role says which features someone can use. It never gives access to a particular document; only a grant from that document's owner does.

There are no folders and no inherited permissions, on purpose: getting access to one file never brings access to others. Grants can carry an expiry date. A document in the trash can be reached by nobody except its owner, and only to restore or purge it.

Where the decision is made

Every request that touches a single document goes through one server function, authorize() in src/authz.js, before anything is read or changed. It reads the live permission table each time. Lists and search apply the same rule inside the database query, so a document you cannot open never appears in results or counts. Hiding a button in the interface is never what protects anything.

When you have no access, the answer is “not found”, whether the document exists or not, so guessing IDs tells you nothing. Document IDs are random UUIDs.

Taking access away

TrustVault never issues share links, download tokens, or signed URLs. The only credential is your session, which is checked on the server on every request. So:

  • Revoking a grant: the person's next request for that document is refused.
  • Deactivating a person: all of their sessions are deleted at once.
  • Changing your password: all of your other sessions end.

The cost is that every download goes through the application server, and a file someone already downloaded cannot be recalled. That copy is why the audit trail matters.

The audit trail

  • Records sign-ins, uploads, views, downloads, edits, deletions, restores, permission changes, sharing suggestions and admin actions, with who, when, from where, and the outcome.
  • Refused attempts are recorded too, with the reason.
  • A download is recorded before the file is sent. If the record cannot be written, the file is not served.
  • The database rejects any update or delete of audit rows.
  • Each entry carries an HMAC of the previous entry's hash plus its own contents. Changing or removing an entry breaks the chain, and the administrator's “Verify” button shows exactly where.
  • Each entry is also written to the server log, a second copy held outside the database.

Leak forensics: every copy is traceable

Access control stops the wrong person. It cannot stop the right person from forwarding what they were given. So TrustVault never hands out the same file twice.

  • Each download gets its own trace ID, stamped into the copy: a visible footer for text and CSV, a comment after the end of a PDF, the archive comment of Word/Excel/PowerPoint files, a metadata chunk in PNG and a comment segment in JPEG. The stored original is never changed.
  • The audit entry records the trace ID and the SHA-256 of the exact bytes that person received.
  • The Leak Tracer takes a leaked file (or its trace ID) and names the download it came from. The file is checked in memory and never stored. Owners can only trace their own documents; administrators can trace everything; every lookup is itself audited.
  • Limits, stated plainly: someone who knows to look can strip a stamp, and a photo of the screen carries none. An unmodified copy still matches by its fingerprint.

Access reviews

Grants go stale after 30 days without confirmation. Owners see them on their Access reviews page and keep or revoke each one, and both decisions are audited. Administrators are alerted to grants nobody has confirmed in 90 days. Every reader can open “Why can I see this?” on a document to see exactly who granted their access.

Files

Uploads are checked against an allow-list, and the file's first bytes must match its extension. Files are encrypted with AES-256-GCM using a key per file, stored under random names outside the web root, and bound to their database record so they cannot be swapped. Downloads are always served as attachments with headers that stop a browser running them.

What this does not protect against

Someone who is legitimately granted a document can still copy what they read. Someone who controls the server and holds the keys could alter the system. These limits, and the others we accepted, are listed in THREATS.md in the repository.
